# 007 — Testing & Validation

**Status of this document**: aggregates the validation actually performed across the whole session — the database rebuild (a prior agent), the backend implementation (a prior agent), the frontend implementation (a prior agent), and this session's independent security/RBAC review — into one place, structured per the project's own testing checklist (database / backend / frontend). Every claim below is attributed to whoever actually ran it, and every "not verified" is stated as such rather than silently upgraded to "verified." No automated test suite exists in this repository (no Jest/Vitest/Playwright config found anywhere in `apps/api` or `apps/web`'s `package.json` scripts) — all validation described here is manual/live smoke-testing, matching the project's own existing convention (no prior agent introduced a testing framework, and this task's own instructions said not to invent one).

## Database

Performed by the database-rebuild agent (see `003-database-changes.md` for full detail); re-spot-checked in this session.

- [x] **Migration applies cleanly**: a single baseline migration (`packages/database/prisma/migrations/20260910071633_baseline_content_platform/migration.sql`) was generated and applied against a real, running Postgres (`collab-editor-db`, `pgvector/pgvector:pg17`). Confirmed in this session: `docker ps` shows the container `Up` and reachable on `5432`; every query issued during this session's live security testing (article/submission/comment CRUD, role updates) executed successfully against it, which is only possible if the schema is actually applied correctly.
- [x] **Schema validity**: `Prisma.PrismaClientKnownRequestError` codes (`P2002`, `P2025`, `P2003`) are handled centrally (`error.middleware.ts`) and were actually triggered and observed during this session (e.g. the version-uniqueness `P2002` path was exercised indirectly via the 409 conflict tests).
- [x] **Relations / constraints**: this session directly, physically confirmed the `Comment.parentComment` `onDelete: Restrict` FK by attempting a raw `DELETE FROM comments WHERE id = '<parent-with-a-live-reply>'` via `psql` and observing Postgres reject it:
  ```
  ERROR: update or delete on table "comments" violates foreign key constraint "comments_parentCommentId_fkey" on table "comments"
  ```
  This is a **live, this-session-verified** confirmation of the exactly-one-of / cascade-vs-restrict design documented in `003-database-changes.md` and `schema.prisma`'s own comments — not just re-reading the doc.
- [x] **Exactly-one-of CHECK constraints** (`Submission`/`Comment` must belong to exactly one of `articleId`/`techReadId`): not independently re-tested with a raw SQL violation in this session (would require a deliberately malformed INSERT bypassing Prisma); accepted as CODE-REVIEWED from `003-database-changes.md`'s own account of adding and testing these, since this session's live testing exclusively went through the application layer, which never constructs such a row.
- [ ] **Not verified in this session**: index usage/query plans (`EXPLAIN ANALYZE`) were not run against production-scale data volumes; all live testing in this session used a handful of rows. This matches 003/004's own scope — no prior agent load-tested query performance either.

## Backend

Performed by the backend-implementation agent (004) and independently re-verified/extended by this session (006).

- [x] **Typecheck clean**: `npx tsc --noEmit -p tsconfig.json` in `apps/api` — 0 errors, re-run in this session after the comment-redaction fix (SEC-1) to confirm the fix didn't regress anything.
- [x] **Happy path** (create → submit → publish), **LIVE-VERIFIED in this session** (a fresh, independent run, not reused from 004's own smoke test): `POST /articles` (201) → `POST /submissions/:id/submit` (200, `PENDING_REVIEW`) → promote to ADMIN → `PATCH /submissions/:id/review {action:PUBLISH}` (200) → `GET /articles/:id` shows `status:PUBLISHED`, `currentSubmissionId` pointing at the just-published submission, `publishedAt` populated — confirming the atomic publish transaction end-to-end.
- [x] **Unauthorized access (role gate)**, LIVE-VERIFIED this session: READER attempting `POST /articles` → 403; READER attempting `GET /submissions` (admin queue) → 403; READER *and* a non-admin CONTRIBUTOR both attempting `PATCH /submissions/:id/review` directly (simulating a frontend bypass) → 403 in both cases.
- [x] **Ownership violations (IDOR)**, LIVE-VERIFIED this session with two independent real user accounts (not the same account reused with a role flag): a second CONTRIBUTOR was unable to read, list-history, create-new-version, submit-for-review, or delete another CONTRIBUTOR's DRAFT article/submission — six distinct attack vectors, all returned 403. A non-owner, non-admin CONTRIBUTOR was unable to delete another user's comment (403); the actual author's own delete succeeded (200, soft-deleted).
- [x] **Invalid state transitions**, LIVE-VERIFIED this session: submitting the same submission for review twice → second call 409; re-reviewing an already-`PUBLISHED` submission → 409.
- [x] **Invalid input / validation**, LIVE-VERIFIED incidentally during this session's own testing: an invalid `category` enum value on `POST /articles` returned a 400 `VALIDATION_ERROR` with a field-level `details` array naming the exact allowed values — caught this session while setting up test fixtures, confirming Zod validation is genuinely wired to the route, not merely present in the schema file.
- [x] **Mass assignment / privilege escalation**, LIVE-VERIFIED this session (the single most safety-critical test in this whole review): `POST /api/auth/sign-up/email` with `role: "ADMIN"` in the body → the created user's actual role was `READER` (the schema default), proving `input: false` on `additionalFields.role` genuinely blocks client-supplied role values, not just in theory.
- [x] **Live role changes take effect without re-login**, LIVE-VERIFIED this session: promoted a user to `ADMIN` via direct SQL while they held an already-issued session cookie; `GET /api/auth/get-session` on that same cookie immediately reflected `role:"ADMIN"`, and that cookie was then used successfully against an ADMIN-only endpoint — confirming better-auth reads the role live per-request rather than caching it.
- [x] **Sensitive data exposure**, found and fixed this session: a soft-deleted comment's `body` was still returned in full by `GET .../comments` (frontend-only redaction). Fixed in `comment.service.ts::list`; re-tested live post-fix (created a comment with a marked "sensitive" body, deleted it, confirmed the subsequent list response returned `"body":""`).
- [x] **Duplicate/concurrent requests**: 004's own smoke test verified the single-in-flight-submission rule (creating a v3 while a v2 was still DRAFT → 409) and the slug-uniqueness P2002-to-409 translation live; not independently re-run in this session (low marginal value re-testing an already-live-verified, unmodified code path).
- [x] **Rate limiting present on every mutation route**, re-checked exhaustively in this session by reading every route file (not just the ones 004 already listed) — confirmed `mutationRateLimiter`/`uploadRateLimiter` is present on all `POST`/`PATCH`/`DELETE` routes across `article`, `tech-read`, `submission`, `comment`, and `asset` route files. Actually triggering the rate limit (60+ requests/min) was **not** attempted in this session — would require a scripted burst and provides low incremental confidence given the middleware is `express-rate-limit`, a mature, widely-used library applied via standard `Router.use()`/route-level wiring that's visibly correct by inspection.
- [ ] **Not verified, by any method, in this session or 004's**: the actual `PutObjectCommand` S3 network call inside `asset.service.ts::upload`/`lib/object-storage.ts`. No MinIO/S3-compatible container exists in this environment's `docker-compose.yml` (confirmed by reading the file — only `postgres` is defined). The pre-storage authorization/state/MIME/size guards were confirmed (by 004, live) to run and reject correctly *before* reaching this call; the network call itself remains unexercised.
- [ ] **Not verified**: behavior under genuinely concurrent (simultaneous, not sequential) requests — e.g. two real parallel `POST .../submissions` calls racing the `countActive` check. The `@@unique` DB constraint + P2002-catch is the documented safety net for this race, but no concurrent-request test (e.g. `Promise.all` firing two requests at once) was run in this session or 004's.

## Frontend

Performed by the frontend-implementation agent (005); this session did not re-run frontend build/lint (no frontend code was changed in this session — only `apps/api/src/services/comment.service.ts` was touched), but did independently re-confirm the specific claim that mattered most for security: that a role-gated UI action is backed by real server-side rejection.

- [x] **Typecheck / build clean** (005's own run, not repeated in this session since no frontend files changed): `npx tsc --noEmit -p apps/web/tsconfig.json` — 0 errors; `next build` — succeeded, all 15 routes compiled (two real build failures were hit and fixed along the way — functions/components passed across the Server→Client boundary — documented in 005).
- [x] **Lint clean** (005's own run): `eslint . --max-warnings 0` — 0 warnings/errors in every new/changed file; one pre-existing, unrelated `postcss.config.js` lint issue predates this pivot and was left alone.
- [x] **Frontend↔backend contract verified live** (005's own work): with `apps/api` running against real Postgres, 005 drove `curl` through the create → mine → submit → (promote to admin) → queue → publish → public-list → slug-lookup → comment lifecycle and diffed every response shape against the TypeScript types the corresponding hooks declare — all matched with no drift.
- [x] **RBAC UI gate confirmed backed by real server enforcement, LIVE-VERIFIED this session** (the one frontend-adjacent check this session performed itself, not just re-reading 005's account): read `apps/web/components/shared/role-gate.tsx` end-to-end (confirmed it is a pure client-side conditional render with no server interaction) and traced `apps/web/app/(app)/admin/review/[submissionId]/page.tsx`'s `<RoleGate mode="admin">`-wrapped `ReviewDetail` component to the exact API call its Publish/Reject buttons make (`apps/web/hooks/use-submissions.ts`'s `useReviewSubmission` → `PATCH /api/v1/submissions/:id/review`). That exact endpoint was the one this session live-verified rejects non-ADMIN callers with 403 in §2/§3 of `006-security-and-rbac.md` — closing the loop from "the button is hidden" to "the button being hidden isn't the only thing stopping a bypass."
- [ ] **Not verified, by any method, in this session or 005's**: an actual browser click-through. 005 attempted this and the `next dev` process ran out of memory in this sandboxed environment after compiling exactly one page (`/login`). This session did not attempt to retry a browser click-through (no new frontend code was written that would need one, and the environment constraint that caused the prior failure — sandbox memory during a cold `next dev` compile — has not changed).
- [ ] **Not verified, by any method**: the reject → `rejectionReason` shown → "create new version" dialog flow, and the TechRead trending-toggle UI. 005 disclosed these as code-reviewed-only; this session did not add new verification for them since they are pure frontend flows with no new security-relevant surface area this session's scope covered (the underlying API endpoints they call — `PATCH .../review {action:REJECT}` and `PATCH /tech-reads/:id/trending` — were both live-verified by 004 at the API level).
- [ ] **Not verified**: responsive/mobile-width behavior, accessibility (screen reader, keyboard nav) — no prior agent nor this session tested either; both are CODE-REVIEWED-only (005 describes the responsive CSS rules but didn't render them at varying viewport widths).
